DAWK v1: Implementation and Validation
Guide
1.0 Introduction to the DAWK Protocol
The Dialectical Adaptive Workbench Kernel (DAWK) is a modular, engineer-ready diagnostics
framework designed to conduct rigorous, reproducible analyses of complex systems. Its
strategic importance lies in bridging the domains of AI interpretability (such as ML-symmetry
diagnostics) and policy governance. This is achieved through a principled architectural
separation: a domain-agnostic computational kernel is decoupled from domain-specific
adapters, allowing for powerful cross-domain reuse while maintaining analytical focus.

The core value propositions of DAWK are rooted in its commitment to determinism, descriptive
restraint, and practical integration. These features ensure that analyses are not only powerful
but also transparent and auditable.

   ●​ Modular Architecture: The framework is built on a kernel-adapter split. The core kernel
      handles universal computations like data normalization, correlation masking, and
      transition analysis. Domain-specific adapters for areas like ML-symmetry or policy
      governance can be plugged in, enabling the reuse of the core logic across different
      research contexts without modification.
   ●​ Reproducibility by Design: Every analysis is governed by a set of typed YAML
      specifications: MetricSpec, DomainSpec, and QuerySpec. These explicit contracts,
      combined with canonical JSON hashing of all inputs and configurations, guarantee that
      outputs are deterministic and fully auditable from end to end.
   ●​ Descriptive Restraint: DAWK is philosophically designed to prevent over-interpretation.
      Normalization rules are sourced from pre-computed calibration artifacts, avoiding the
      data leakage and biases inherent in sweep-fitted scaling. Furthermore, the protocol
      generates mechanical audit logs and explicit caveats, ensuring that all findings are
      presented with appropriate context and humility.
   ●​ Actionable and Practical: The framework is engineered for low integration overhead,
      designed to fit seamlessly into existing research workflows. It can act as a drop-in
      analysis tool for data generated by PyTorch-based experimental sweeps or policy
      simulations from frameworks like RMAGS.

To ensure a successful and robust deployment, this guide outlines a structured, four-stage
validation path. This methodology provides a systematic approach to implementing, verifying,
and integrating the DAWK framework into your research environment.
2.0 The Four-Stage Validation Path: An Overview
The implementation of the DAWK protocol follows a structured, four-stage validation path. This
path is designed to move systematically from initial configuration to a fully integrated and
validated pilot, ensuring robustness, correctness, and reproducibility at each step. By
completing each stage in sequence, developers can build confidence in the framework's
behavior before deploying it in live research workflows.

The four stages provide a clear roadmap for bringing the DAWK workbench online:

   1.​ Stage 1: Artifact Generation and Setup: Defining the operational contracts of the
       analysis through canonical YAML and JSON configuration files.
   2.​ Stage 2: Skeleton Implementation: Developing the core Python module with all
       necessary functions for normalization, correlation, clustering, and transition analysis.
   3.​ Stage 3: Internal Dry-Run: Validating the implementation's core invariants using
       synthetic or retrospective data before exposing it to live systems.
   4.​ Stage 4: Pilot Integration and Iteration: Integrating the validated workbench into live
       research workflows and monitoring key performance metrics for continuous refinement.

The following sections provide detailed instructions for executing each stage, beginning with the
foundational step of artifact generation.


3.0 Stage 1: Artifact Generation and Setup
The foundation of any DAWK analysis is a set of explicit, version-controlled configuration
artifacts. This stage involves creating the three core YAML specifications and the supporting
JSON calibration files that govern the entire workflow. These artifacts ensure determinism by
codifying every aspect of the analysis, from metric definitions to the precise scope of a query,
providing a clear and auditable statement of intent.

3.1 MetricSpec: Defining Metric Contracts

The metric_spec.yaml file functions as the master contract for all metrics used within the
DAWK framework. It explicitly defines each metric's type, the normalization transform to be
applied, and a direct link to a version-controlled calibration source. This pre-registration
prevents ad-hoc data treatment and ensures consistent processing.

3.2 DomainSpec: Defining Analysis Domains

The domain_spec.yaml file defines the structure of different research domains, such as
ml_symmetry or policy_governance. It specifies the identifying facets for an experimental
cell (e.g., model, dataset, seed), lists the required data columns, and defines how cross-domain
analysis should be handled.

# domain_spec.yaml
version: "dawk.domain_spec.v1"

domains:
 ml_symmetry:
  domain_name: "ml_symmetry"
  cell_id_facets: [dataset, model, action, mask, lambda, prime, seed]
  required_columns: [cell_id, phase_index, phase_label, asi_mode]
  metric_allowlist: [acc_unseen, delta_sym_mean, mi_rel_post, asi_median, w_t]
  generator:
   kind: "none"
 policy_governance:
  domain_name: "policy_governance"
  cell_id_facets: [scenario, governance_mode, intervention, budget, seed]
  required_columns: [cell_id, phase_index, phase_label, asi_mode]
  metric_allowlist: [equity_score, stability_proxy, compliance_rate]
  generator:
   kind: "posg"
   params:
     n_rollouts: 200
     horizon: 50
     seed: 1337

cross_domain:
 default: "none" # none | mapping_only
 mapping_sets:
   - name: "ai_policy_v1"
     path: "mappings/ai_policy_v1.yaml"
     sha256: "<fill>"


A key feature of this specification is the generator block. It enables the use of hooks to
produce synthetic data rows, such as triggering POSG (Partially Observable Stochastic Game)
rollouts for RMAGS policy simulations. Additionally, the default setting cross_domain:
"none" is a crucial element of descriptive restraint, preventing accidental or unjustified
comparisons between disparate domains unless explicitly enabled.

3.3 QuerySpec: Defining Bounded, Auditable Queries

The query_spec.yaml file defines the precise scope of a single, bounded analysis. It
specifies exactly which domains, phases, metrics, and phase-pairs to include, ensuring that
each run is focused and deterministic. This prevents scope creep and makes each analysis a
discrete, auditable event.

over-interpretation of results.

3.4 Calibration Artifacts: Sourcing Normalization Rules

In the DAWK protocol, all normalization transforms are sourced from pre-computed calibration
artifacts, typically stored as calib/*.json files. These files contain statistical summaries (e.g.,
quantiles) derived from a representative corpus of data, entirely separate from the data being
analyzed.

This design choice is critical for analytical integrity. By decoupling normalization from the
immediate dataset, it prevents data leakage and the biases associated with fitting scaling
parameters (like z-scoring) to the data under investigation. This ensures that metrics from
different runs or experiments are comparable on a common scale.

dawk/hashutil.py: The determinism and reproducibility module.

This utility module provides functions for creating deterministic, canonical hashes of
configuration objects and other text-based artifacts. These hashes are fundamental to DAWK's
reproducibility guarantee.

from __future__ import annotations
import hashlib
import json
from typing import Any, Dict

def canon_json(obj: Any) -> str:
  return json.dumps(obj, sort_keys=True, separators=(",", ":"), ensure_ascii=False)

def sha256_hex(data: bytes) -> str:
  return hashlib.sha256(data).hexdigest()

def hash_json(obj: Any) -> str:
  return sha256_hex(canon_json(obj).encode("utf-8"))

def hash_text(text: str) -> str:
  return sha256_hex(text.encode("utf-8"))

def header_hash(header: Dict[str, Any], domain_tag: str = "DAWK_HEADER_v0") -> str:
  canon = f"{domain_tag}|{canon_json(header)}"
  return hash_text(canon)


Analysis: The canon_json function is critical. By sorting keys and removing whitespace, it
ensures that two dictionaries with the same content will always produce the exact same JSON
string, and therefore the same hash, regardless of their in-memory representation.
dawk/calibration.py: The normalization sourcing module.

This module is responsible for loading the pre-computed calibration artifacts from JSON files
and providing a safe interface for accessing the necessary quantile values for normalization.

from __future__ import annotations
import json
from dataclasses import dataclass
from typing import Any, Dict, Mapping

@dataclass(frozen=True)
class Calibration:
   version: str
   domain: str
   metrics: Dict[str, Dict[str, float]]

def load_calibration(path: str) -> Calibration:
  with open(path, "r", encoding="utf-8") as f:
      raw = json.load(f)
  return Calibration(
      version=raw["version"],
      domain=raw.get("domain", "unknown"),
      metrics=raw["metrics"],
  )

def get_quantiles(calib: Calibration, metric: str, fields: list[str]) -> Dict[str, float]:
  if metric not in calib.metrics:
     raise KeyError(f"Metric '{metric}' missing in calibration.")
  m = calib.metrics[metric]
  out: Dict[str, float] = {}
  for k in fields:
     if k not in m:
         raise KeyError(f"Calibration field '{k}' missing for metric '{metric}'.")
     out[k] = float(m[k])
  return out


Analysis: The get_quantiles function enforces the contract specified in MetricSpec. It will
raise a KeyError if a metric or a required calibration field (e.g., q95) is missing, preventing
silent failures and ensuring the analysis halts if its preconditions are not met.

dawk/normalize.py: The calibration-based transformation module.
This module contains the logic for applying the various normalization transforms defined in the
MetricSpec. It operates strictly on the parameters provided by the loaded calibration artifacts.

from __future__ import annotations
import math
import numpy as np
import pandas as pd
from typing import Dict, Tuple
from .types import MetricSpecEntry
from .calibration import Calibration, get_quantiles

_EPS = 1e-12

def _logit(p: float) -> float:
  p = min(max(p, _EPS), 1.0 - _EPS)
  return math.log(p / (1.0 - p))

def _winsor(x: float, lo: float, hi: float) -> float:
  return min(max(x, lo), hi)

def normalize_series(
   s: pd.Series,
   metric: str,
   spec: MetricSpecEntry,
   calib: Calibration,
) -> Tuple[pd.Series, Dict[str, float]]:
   """
   Returns normalized series + params used (for diagnostics table).
   Normalization maps values into a comparable (but still descriptive) scale using calibration
quantiles.
   """
   transform = spec["transform"]
   fields = spec.get("calibration_fields", [])
   q = get_quantiles(calib, metric, fields) if fields else {}

  params: Dict[str, float] = {}
  x = s.astype("float64")

  if transform == "identity":
      return x, params

  if transform == "rank_quantile":
      # Monotone mapping: ranks -> [0,1] (ties averaged)
      r = x.rank(method="average", na_option="keep")
     denom = float(r.notna().sum())
     if denom <= 1:
         return pd.Series(np.nan, index=s.index), {"n_nonnull": float(denom)}
     out = (r - 1.0) / (denom - 1.0)
     return out, {"n_nonnull": float(denom)}

  if transform == "winsor_quantile":
      lo, hi = q["q01"], q["q99"]
      params.update({"winsor_lo": lo, "winsor_hi": hi})
      w = x.map(lambda v: _winsor(v, lo, hi) if pd.notna(v) else np.nan)
      # robust affine scaling by (q99 - q01)
      denom = max(hi - lo, _EPS)
      out = (w - lo) / denom
      return out, params

  if transform == "affine_quantile":
      lo, mid, hi = q["q05"], q["q50"], q["q95"]
      params.update({"q_lo": lo, "q_mid": mid, "q_hi": hi})
      denom = max(hi - lo, _EPS)
      out = (x - lo) / denom
      return out, params

  if transform == "logit_quantile":
      lo, mid, hi = q["q05"], q["q50"], q["q95"]
      params.update({"q_lo": lo, "q_mid": mid, "q_hi": hi})
      # apply logit to probabilities, then affine by logit(q95)-logit(q05)
      lo_l, hi_l = _logit(lo), _logit(hi)
      denom = max(hi_l - lo_l, _EPS)
      out = x.map(lambda v: (_logit(v) - lo_l) / denom if pd.notna(v) else np.nan)
      return out, params

  raise ValueError(f"Unknown transform: {transform}")

def add_kurtosis_if_enabled(x: pd.Series, enabled: bool, min_n: int) -> Dict[str, float]:
  if not enabled:
      return {}
  v = x.dropna().values
  if v.size < min_n:
      return {"kurtosis_n": float(v.size)}
  # Fisher kurtosis (excess), descriptive only
  m = float(np.mean(v))
  s2 = float(np.mean((v - m) ** 2))
  if s2 < _EPS:
      return {"kurtosis": 0.0, "kurtosis_n": float(v.size)}
  k = float(np.mean((v - m) ** 4) / (s2 * s2) - 3.0)
  return {"kurtosis": k, "kurtosis_n": float(v.size)}


Analysis: The normalize_series function is the heart of DAWK's descriptive restraint. It
contains no logic for "fitting" parameters from the input series s. Instead, every transform relies
exclusively on the quantile dictionary q, which is populated directly from the external calib
object. This design choice is fundamental to preventing data leakage.

dawk/spearman.py: The masked correlation and tie-accounting module.

This module computes pairwise Spearman rank correlations. It correctly handles missing data
by using only pairwise-complete observations and includes functionality to account for the
fraction of ties in the data, which can influence correlation estimates.

from __future__ import annotations
import numpy as np
import pandas as pd
from scipy.stats import spearmanr
from typing import List, Tuple
from .types import CorrMatrix, SpearmanResult

def _tie_fraction(a: np.ndarray) -> float:
  if a.size <= 1:
      return 0.0
  # fraction of values involved in ties (coarse but deterministic)
  _, counts = np.unique(a, return_counts=True)
  tied = counts[counts > 1].sum()
  return float(tied) / float(a.size)

def spearman_pair(x: pd.Series, y: pd.Series) -> SpearmanResult:
  m = x.notna() & y.notna()
  xv = x[m].astype("float64").values
  yv = y[m].astype("float64").values
  n = int(xv.size)
  if n < 2:
      return SpearmanResult(rho=float("nan"), n_pairs=n, tie_frac=float("nan"))
  rho, _ = spearmanr(xv, yv)
  tie = max(_tie_fraction(xv), _tie_fraction(yv))
  return SpearmanResult(rho=float(rho), n_pairs=n, tie_frac=float(tie))

def spearman_matrix(df: pd.DataFrame, metrics: List[str]) -> CorrMatrix:
  k = len(metrics)
  rho = np.full((k, k), np.nan, dtype="float64")
  n_pairs = np.zeros((k, k), dtype="int64")
  tie_frac = np.full((k, k), np.nan, dtype="float64")

   for i in range(k):
      rho[i, i] = 1.0
      n_pairs[i, i] = int(df[metrics[i]].notna().sum())
      tie_frac[i, i] = _tie_fraction(df[metrics[i]].dropna().astype("float64").values) if n_pairs[i, i] > 1
else 0.0

  for i in range(k):
     for j in range(i + 1, k):
         r = spearman_pair(df[metrics[i]], df[metrics[j]])
         rho[i, j] = rho[j, i] = r.rho
         n_pairs[i, j] = n_pairs[j, i] = r.n_pairs
         tie_frac[i, j] = tie_frac[j, i] = r.tie_frac

  return CorrMatrix(metrics=metrics, rho=rho, n_pairs=n_pairs, tie_frac=tie_frac)


Analysis: The _tie_fraction function provides a deterministic, if coarse, measure of how
much the data is affected by tied ranks. Logging this value alongside the correlation coefficient
is crucial for context, as a high tie fraction can reduce the reliability of the Spearman rho
estimate.

dawk/clustering.py: The linkage and stability analysis module.

This module provides functions for hierarchical clustering based on the computed correlation
distances. Crucially, it includes a method for assessing the stability of clustering results across
different linkage methods.

from __future__ import annotations
import numpy as np
from scipy.cluster.hierarchy import linkage, cophenet, fcluster
from scipy.spatial.distance import squareform
from sklearn.metrics import adjusted_rand_score
from typing import Dict, List, Tuple
from .types import Linkage, DistanceKind

def corr_distance_matrix(rho: np.ndarray) -> np.ndarray:
  # 1 - rho (approximation; may be non-metric under masking/ties)
  d = 1.0 - rho
  np.fill_diagonal(d, 0.0)
  return d

def l1_shared_distance_matrix(X: np.ndarray) -> np.ndarray:
  # X: (n_items, n_features) already masked to shared-support features
  n = X.shape[0]
  d = np.zeros((n, n), dtype="float64")
  for i in range(n):
     for j in range(i + 1, n):
         v = float(np.mean(np.abs(X[i] - X[j])))
         d[i, j] = d[j, i] = v
  return d

def build_linkage_and_cophenetic(
   dist_sq: np.ndarray,
   method: Linkage,
) -> Tuple[np.ndarray, np.ndarray]:
   # dist_sq: square distance matrix
   dist_vec = squareform(dist_sq, checks=False)
   Z = linkage(dist_vec, method=method)
   coph_dists, _ = cophenet(Z, dist_vec)
   # note: scipy returns scalar correlation in coph_dists in some versions; keep robust:
   # We also want cophenetic pairwise distances; compute via cophenet's returned distances
not exposed.
   # Practical approach: reconstruct cophenetic distances by cutting at all merges (expensive),
   # so here we store linkage Z and rely on Z for plots; range diagnostics use ARI stability
below.
   return Z, dist_vec

def ari_stability_across_linkages(
   dist_sq: np.ndarray,
   methods: List[Linkage],
   cut_k: List[int],
) -> Dict[str, Dict[int, float]]:
   """
   Deterministic: uses fcluster with criterion 'maxclust' for each k.
   Returns ARI(methodA_vs_methodB)[k] averaged across pairs; also keep raw if you prefer.
   """
   dist_vec = squareform(dist_sq, checks=False)
   Zs = {m: linkage(dist_vec, method=m) for m in methods}
   labels = {m: {k: fcluster(Zs[m], k, criterion="maxclust") for k in cut_k} for m in methods}

  out: Dict[str, Dict[int, float]] = {}
  for k in cut_k:
     vals: List[float] = []
     for i in range(len(methods)):
        for j in range(i + 1, len(methods)):
            a, b = methods[i], methods[j]
           vals.append(float(adjusted_rand_score(labels[a][k], labels[b][k])))
     out[f"ari_avg_k{k}"] = {k: float(np.mean(vals)) if vals else float("nan")}
  return out


Analysis: The function ari_stability_across_linkages provides a crucial stability
metric. Instead of claiming one linkage method is "best," it measures the agreement between
partitions produced by different methods (e.g., 'single', 'complete', 'average') using the Adjusted
Rand Index (ARI). A high average ARI suggests the discovered cluster structure is robust, while
a low ARI suggests it is sensitive to the choice of algorithm, which is a key descriptive insight.

dawk/transitions.py: The phase-to-phase accounting module.

This module is responsible for analyzing how experimental cells transition between phases. It
provides precise accounting of which cells are added, dropped, or shared between two phases
of an experiment.

from __future__ import annotations
import pandas as pd
from typing import Dict, Tuple
from .types import TransitionAccounting

def transition_join(
   df_a: pd.DataFrame,
   df_b: pd.DataFrame,
   key: str = "cell_id",
   exclude_mask_col: str = "excluded",
) -> Tuple[pd.DataFrame, TransitionAccounting]:
   """
   Joins phase A and B rows. Exclusions are rows where excluded==True in either phase.
   """
   a = df_a[[key, "asi_mode", exclude_mask_col]].copy()
   b = df_b[[key, "asi_mode", exclude_mask_col]].copy()

  n_a, n_b = len(a), len(b)
  merged = a.merge(b, on=key, how="outer", suffixes=("_a", "_b"), indicator=True)

  added = int((merged["_merge"] == "right_only").sum())
  dropped = int((merged["_merge"] == "left_only").sum())
  shared = int((merged["_merge"] == "both").sum())

  # Excluded if either side excluded==True (missing treated as False)
  ex_a = merged[f"{exclude_mask_col}_a"].fillna(False)
  ex_b = merged[f"{exclude_mask_col}_b"].fillna(False)
  excluded = (ex_a | ex_b)
  n_ex = int(excluded.sum())
  merged["excluded"] = excluded

  acc = TransitionAccounting(
     phase_a=int(df_a["phase_index"].iloc[0]),
     phase_b=int(df_b["phase_index"].iloc[0]),
     n_a=n_a,
     n_b=n_b,
     n_shared=shared,
     n_dropped=dropped,
     n_added=added,
     n_excluded=n_ex,
  )
  return merged, acc

def mode_transition_matrix(merged: pd.DataFrame) -> pd.DataFrame:
  """
  Returns contingency of asi_mode_a -> asi_mode_b on shared, non-excluded rows.
  """
  m = merged[(merged["_merge"] == "both") & (~merged["excluded"])].copy()
  # missing modes are kept explicit
  c = pd.crosstab(m["asi_mode_a"], m["asi_mode_b"], dropna=False)
  return c


Analysis: The transition_join function provides a complete census of the data across two
phases. By explicitly calculating n_shared, n_dropped, and n_added, it gives a clear picture
of the stability and composition of the experimental population over time.

5.0 Stage 3: Internal Dry-Run and Validation
The internal dry-run is a critical stage for verifying the correctness of the implementation against
known inputs before integrating it into larger, more complex systems. The objective is to confirm
that the Python skeleton behaves as expected and that its core invariants—such as
determinism and adherence to masking rules—are upheld.

The dry-run procedure is straightforward:
   1.​ Prepare Test Data: Create a small, synthetic DataFrame in memory (e.g., 50-100 rows,
       3 phases) or use retrospective data from past experiments, such as simulated sweeps
       from historical project versions like SAAP v7-18. This data should contain all columns
       required by the DomainSpec.
   2.​ Execute the Workbench: Run the implemented cli.py script from the command line,
       pointing it to the test data CSV file and the configuration artifacts (MetricSpec,
       DomainSpec, QuerySpec) created in Stage 1.
   3.​ Validate Invariants: Inspect the generated output files (e.g., bundle.json) to verify
       that the implementation meets the following success criteria.

The following invariants must be validated to confirm the implementation is correct:

   ●​ Hash Stability: Verify that the output bundle hashes in bundle.json (e.g.,
      header_hash, metric_spec_hash) are stable. Running the exact same command
      with identical inputs must produce an identical output bundle hash every time.
   ●​ Masking Fraction: For a well-constructed test dataset, the observed mask_frac in the
       dendro_stability output should be low (target <10%), well below the hard limit of
       max_mask_frac (e.g., 0.5) defined in the QuerySpec.
   ●​ ARI Stability: Check the ari values in the dendro_stability output. The average
      Adjusted Rand Index (ARI) for clustering stability across linkages should meet the target
      of >0.6. A value above 0.5 may be acceptable but warrants investigation into the stability
      of the discovered clusters.

Once these invariants are validated, the DAWK implementation is considered correct and is
ready for pilot integration with live research pipelines.

This final stage marks the transition of the DAWK framework from a validated tool to an active
